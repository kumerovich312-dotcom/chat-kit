### Nextbot в Атласе — что переносим в подключение

- **Приём:** `POST /api/nextbot/events`, ключ `Authorization: Bearer nb_…` (или `X-Api-Key`), тело до 1 МБ, JSON-объект.
  События: `client_message`, `bot_message`, `manager_message`, `lead`, `ping`, `vacancies` (+ синонимы). Поля ищутся
  по спискам вариантов во всём теле и в `args` (верхний уровень важнее).
- **«Полный диалог»** (дамп всей переписки строками `22.09.26 20-21 [Автор]: текст`, время — UTC, до минуты): берём конец
  (60 000 знаков), раскладываем на реплики; ключ повтора строки — `nb:<диалог>:<sha1(время|автор|текст)[0..32]>` —
  **менять нельзя**: по нему Атлас узнаёт уже записанные строки. Время строки: минута из дампа, но строго после
  предыдущей известной реплики («пол»); последняя реплика клиента — «сейчас» в пределах своей минуты.
- **Кто ответил:** Nextbot подписывает одинаково и бота, и менеджера с телефона. Если сценарий «Новое сообщение агента»
  настроен (были события `bot_message` за 14 дней) или пришло `VALIDATE_ACCESS_DIALOG_PAUSED`, незнакомый ответ из дампа —
  «менеджер с телефона»; позже пришедшее событие бота с тем же текстом исправляет автора на «бот».
- **Время события:** поле `time` = «Текущее дата/время (текст)» с секундами; пояс Nextbot — по разнице с часами (шаг 30 мин);
  из будущего или старше 6 часов — не берём. Время без секунд — не берём.
- **Повторы:** `nb:<message_id>`, без него — sha1(диалог|тип|текст|дамп|10-секундное окно).
- **«Передаю менеджеру»** — регулярка `HANDOFF` → `handoff = true`: клиент снова ждёт человека.
- **Тестовый чат** («Тестовый чат» / WindowChat) — мимо CRM. «test value» — подсказка про пробный запуск.
- **Файлы:** ссылки только с хранилищ мессенджера (`*.digitaloceanspaces.com`, `storage.nextbot.ru`); фото в дампе — одним
  именем файла, ищется в папках хранилища (`media_folders`); знакомую ссылку не качаем; тот же файл по содержимому — один
  раз (sha1); плохие ссылки час не пробуем; скачивание — после ответа Nextbot (`after`), место в истории — сразу за
  сообщением события.
- **Отправка:** POST на «Ссылку вебхука» (только https на `*.nextbot.ru`, без перенаправлений, 10 с): `forwarded_output`
  (клиенту), `output` (заметка боту «не перебивай менеджера» — при первом ответе менеджера за 6 часов), `notification`
  (служебная отметка), файл — `image_url` / `document_url` по временной подписанной ссылке на сутки.
- **Остаётся в Атласе:** клиенты / сделки / воронки, «Возможный дубль», `nextbot_dialog_aliases` после объединения
  карточек, заявка `lead` (поля сделки и анкеты), функция `vacancies`, журнал обмена `nextbot_events`, настройки.

## TishCRM — шлюз WhatsApp `apps/wa-gateway` (клон 585c30d, только чтение)

Отдельный процесс Node, библиотека Baileys, одна сессия WhatsApp на клинику (подключение по QR, как WhatsApp Web).
**Сообщения шлюз передаёт не через HTTP, а через общую с кабинетом базу Postgres:**

- **Входящее** (`messages.upsert`, только личные чаты `@s.whatsapp.net` и `@lid`): повтор отсекается по
  `messages.wa_message_id`; диалог — `dialogs` по `(org_id, wa_jid)`, где `wa_jid` — телефонный адрес, если известен
  (`senderPn` у `@lid`), `wa_alt_jid` — адрес как пришёл; пациент привязывается по последним 9 цифрам телефона;
  файл скачивается сразу в `uploads/org_<id>/wa/<id сообщения>.<расширение>`; строка `messages`: `direction 'in'`,
  `author 'patient'`, `body`, `wa_message_id`, `wa_remote_jid`, `media_type` (image / video / sticker / audio / voice /
  document), `media_path`, `media_mime`, `media_name`. Потом шлюз зовёт кабинет: `POST /api/internal/events`
  с общим токеном шлюза и кабинета и телом `{ event: "message_in", org_id, dialog_id }` — только «пациент написал»,
  сам текст уже в базе.
- **Сообщение с телефона клиники** (`fromMe`): `author 'phone'`, `delivery 'sent'`; эхо сообщения, отправленного из CRM,
  узнаётся по тексту за 2 минуты у строки с пустым `wa_message_id` — дубля нет.
- **Исходящее из CRM:** CRM кладёт строку в таблицу-очередь `wa_outbox` (`org_id, wa_jid, body, media_path, media_type,
  media_mime, media_name, message_id, status`), шлюз раз в 1,5 с забирает `pending → sending` (`FOR UPDATE SKIP LOCKED`),
  отправляет и ставит `sent` / `failed`; `messages.wa_message_id` и `delivery = 'sent'`. Адрес `nb:<номер диалога>` —
  диалог Nextbot: шлюз отвечает через вебхук Nextbot (`nextbot.mjs`, те же правила, что в Атласе: `forwarded_output`,
  заметка боту `output` при первом ответе сотрудника за 6 часов, файл — подписанной ссылкой `/api/pub/media/<id>` на сутки).
- **Статусы:** `messages.delivery` pending → sent → delivered → read, только вверх; прочитано оператором
  (`dialogs.read_pending`) — шлюз отправляет в WhatsApp отметку «прочитано» (`messages.receipted`).
- **ИИ-ответ в самом шлюзе** (Claude, если у клиники `orgs.ai_enabled`): `dialogs.status` new / ai / operator / closed;
  при `operator` ИИ молчит («пауза»); ИИ может передать диалог оператору (`handover`) и создать запись на приём.
  Автор ответа ИИ — `author 'ai'`. Сотрудник из CRM — `author 'operator:<имя>'`.
- **Напоминания о визите** за 24 часа — через ту же очередь.
- **HTTP-API шлюза — только управление** (тот же общий токен, иначе 401): `POST /connect {orgId}` — начать подключение (QR появляется в таблице
  `wa_sessions`: `status` waiting_qr / connected / disconnected, `qr`, `wa_number`), `POST /disconnect {orgId}`,
  `POST /nextbot-test {orgId, dialogId, text}`. Отдельной команды «отправить» по HTTP нет — только очередь в базе.

Вывод для набора: подключение «шлюз TishCRM» = управление по HTTP (подключить / отключить / проверить) + очередь `wa_outbox`
и приём событий `message_in` через «переходник» проекта (у TishCRM общая база со шлюзом).
